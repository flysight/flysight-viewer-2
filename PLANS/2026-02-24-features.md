# FlySight Viewer Features

In this document, I just want to spitball what I see as some of the main features/goals in FlySight Viewer 2. This is going to be a fairly unstructured document, with the main goal being to get everything down on the page, so we can pull coherent features out of it later.

What's written here should not be taken as an absolute specification for the software. Some of this is inexact, or may not express the most efficient way to implement a feature. More than anything, I'm trying to capture the *shape* of the software as I see it in my head.

## Sessions

Let's start with the most basic form of data. Each session is a set of data recorded during a single active session on a FlySight. The data is stored as:

* **Attributes**: This are top-level variants that describe some individual attribute of the session. These can include things like the firmare version used, ground elevation, current winds, exit time, etc.
* **Sensors**: Each sensor is a grouping of individual **measurements** which share a common timebase. So there is a single vector of real-valued times and several vectors of real-valued measurements. For example, the GNSS receiver returns 3D position and velocity for each time; the IMU returns 3D acceleration and rotation for each time.
* **Measurements**: A measurement is a single value measured at each moment in time by this sensor. For example, for GNSS this could be latitude, longitude, elevation, 3D velocity, accuracy estimates, and the number of satellites used in the fix.

Attributes, sensors, and measurements are all identified by a unique string (for sensors/measurements, strictly a unique string pair). So, for example, we might have the "FW_VER" string, the "GNSS" sensor, and the "GNSS/hAcc" measurement.

## Calculated Attributes and Measurements

Attributes and measurements can correspond to raw measurements, like the ones mentioned above, but they can also correspond to calculated values. For example, the maximum vertical speed in a particular track could be stored as a calculated attribute. We can also have calculated measurements, for example, a representation of the track in a uniform x/y/z coordinate system; or even a simplified representation of the track where we delete any point that can be interpolated from its neighbours with some level of accuracy. Since the last one requires a new timebase, it's actually a separate sensor from the source data. The same would be true of a sensor fusion dataset generated from GNSS and IMU data.

## Calculations

Each calculated attributes/measurement is the result of some calculation. These calculations take a set of attributes/measurements (any combination of the two) and produce a set of attributes/measurements (again any combination). They should be idempotent, in the sense that they produce the same data if the calculation is repeated.

Currently, this is implemented as "calculated attributes" and "calculated measurements" with lazy evaluation as well as a mechnism for managing dependencies--when one value changes, we need to determine which other values must be recalculated. However, this has some limitations, e.g.:

* This can't represent calculations which have multiple outputs, without also adding side effects to the calculation itself.
* This won't be suitable for calculations which may take a longer time. For example, sensor fusion may take several seconds or minutes. In the long run, I envision having a "calculation dock" where these long-running calculations are listed along with progress information, the ability to stop the calculation, etc. Not all calculations will belong in this dock. Some can be computed quickly, and should continue to be computed automatically in a lazy fashion.

We'll still want to manage dependencies for these calculations. For long-running calculations, we would just invalidate or delete the old results and maybe flag the calculation as being needed--e.g., it could be added to the calcualtion dock with a play button next to it.

## Definition of plots, calculations, etc.

Plots and calculations should be defined in a central way. This isn't to say they should be defined in the same place, but one thing I think we're doing right in the current code is that plots, calculations, plot tools, docks, markers, etc., are all defined in one place, and then the feature is fleshed out separately. This makes it really easy to add new items.

## Plots

A plot shows a specific sensor/measurement as a line in the plot dock. The plot is associated with things like line colour and units. Plots can be turned on/off in the plot selection dock, and some can be turned off with single-key shortcuts, or in the Plots menu.

## Plot Dock

The plot dock houses a chart showing the currently visible plots for each visible session, as well as markers above the chart area. This can get crowded when there are a lot of visible plots/sessions, so we've implemented keyboard modifiers to aid with navigation.

1. When Shift is held, the cursor model applies to all sessions which have data at the current time. This allows the user to scan across the plot and see how all the visible sessions interact in other docks.
2. When Ctrl is pressed, the cursor model "locks" onto the current focused model. This allows the user to scan across the the plot and see how a single visible session changes over time.

Currently, these are not implemented in other docks, but they would probably be a good fit for the map dock and for cross-plots.

## Unit Conversion

Currently, the user can select between metric and imperial units for plot and legend displays, but we've factored out unit definition and conversion in a way which makes it easy to add other units (e.g., nautical units or SI units) down the road if we want to.

In addition to specific units (e.g., "km") the unit conversion system defines unit types (e.g., "distance" or "altitude") so the preferred unit for a particular measurement system isn't necessarily the same for every measurement using a given SI unit (e.g., "m"). For example, in imperial units, distance might be specified in miles, but altitude would be specified in feet, even though both are stored internally in meters.

## Markers

Similiarly, markers show a specific time attribute in the plot dock. These are drawn as a sort of "thought bubble" above the plot. I think these will wind up being a very powerful feature.

For example, I want to extend the "Time from exit" x-axis mode for the plot dock so that it's really "Time from marker". The default could be exit, but what I have in mind is that by double-clicking on a marker, the user can change which marker plots line up at. So, for example, we might have a "MAXVZ" marker which gives the time of maximum vertical speed. A canopy pilot, who tries to generate as much energy as they can in a dive just before landing, could double-click on one of these markers, and all visible sessions would line up at that marker. This simplifies analysis of the time span around that event.

Some markers might be based on calculated attributes, like the time of maximum vertical speed mentioned above, but others might be based on literal attributes, like exit time or video playback time. These could be dragged in the plot dock in order to adjust their position.

For calculated markers, I would like the interface to support at least:

* Plot value equals some reference value
* Plot value minimum/maximum
* Time window based on other markers, e.g., "Only after exit"

Maybe we can implement a fairly simple interface for these features in the application, and leave more complex features for the embedded Python interface.

One thing I want to keep an eye on is the distinction between markers, which mark the time at which some event occurs, and the value of a specific plot at that time. For example, in this document I sometimes go back and forth between talking about a maximum vertical speed marker, which strictly speaking marks the time at which maximum vertical speed occurs (this would essentially be a user-facing representation of a "maximum vertical speed time" attribute); and a maximum vertical speed attribute, which would indicate the actual value of maximum vertical speed for that session. Given the way I tend to confuse these two features, I wonder if they should really be one feature, but sliced in a slightly different way.

## Scoring and Analaysis

Let's talk about scoring first. I want to use FlySight Viewer 2 to score skydiving competitions like the Wingsuit Performance competition. I envision this as being just another calculaltion--you hand it a set of measurements which define the performance (e.g., 3D position) plus a set of attributes which define scoring parameters--e.g., the top and bottom of the scoring window, or the current task (time, distance, or speed)--and it returns an attribute which gives the score for that jump.

We could handle other analysis the same way. For example, given a canopy piloting session, we could have a set of calculations which provide relevant attributes for canopy pilots, like maximum horizontal speed, maximum vertical speed, roll-out height, etc. These could all be stored as attributes for the session.

## Logbook

The logbook dock shows each session as a row, with each column being an attribute of that session. In addition, on the left edge there is a check box to control session visibility. In the long run, I imagine this being used for long-term analysis. For example, a canopy pilot who has used the analysis described above to produce maximum vertical speed and maximum horizontal speed for each of their sessions could use the logbook to create a scatter plot of maximum vertical speed vs. maximum horizontal speed.

Ulltimately, I want the logbook to be persistent. This will mean that each track which gets imported is stored in some format on the user's computer, along with an created attributes/measurements. It may also be helpful to store calculated attributes/measurements, but we'll have to weigh the benefit of this against the space taken on disk. Generally, I'd like things to be stored in a "FlySight Viewer" folder, e.g., in the user's Documents folder, or wherever is most "standard". I'd like things to be stored as text, so that users can easily write their own software to analyze the data. The format could reflect FlySight 2's format, which is capable of storing any number of attributes/sensors/measurements, but it might also be beneficial, e.g., to store it in a format like JSON.

What I have in mind is to store attributes in a sort of "database" at the top level, which can be loaded quickly to populate the logbook when the application starts. Then sensors/measurements could be organized maybe in folders associated with each session. I'm not set on any particular organization here, but I would like it to be as transparent as possible to the user, while maintaining some basic performance requirements. One of the strengths of FlySight is that it generally uses open and transparent document formats, so that users can read it using their own software with minimal documentation required.

It should be very easy to back this data up, and the format should be robust enough that it's difficult to corrupt it. Users might invest a lot of time in building analysis into the logbook, so I want to be as sure as we can be that they aren't going to lose this data because of a simple mistake or system error.

## Cross-plots

With the foundation set out above, it should be very easy to create new cross-plot docks which are based on a plot of one measurement vs. a second measurement for all visible sessions (line charts), or a plot of one attribute vs. a second attribute for all visible sessions (scatter charts), or various other combinations we might imagine. Other than the scatter plot mentioned above, three line charts come to mind:

* **Drag polar**: We can estimate the lift and drag coefficients based on velocity data and plot these as a drag polar. The plot could be derived from a simple cross-plot, but could add analysis features like max L/D. In this way, we could use the plot to analyze single jumps, or to compare many jumps.
* **Speed polar**: Similarly we can use cross-plots to plot vertical speed vs. horizontal speed, and use this to determine things like maximum glide ratio, the effect of wind, etc.
* **Wind circle**: If we plot 2D horiontal velocity as a polar plot, we can determine wind speed and aircraft speed when the aicraft travels through a wide range of headings. Again, an additional analysis layer could fit a circle to the data and calculate/display attributes for wind speed and aircraft speed for each visible session.

## Video Synchronization

At the moment, video sync is achieved by choosing a sync frame in the video and choosing a moment in a particular track to associate with that frame. During video playback, a cursor is drawn in the plot dock showing what UTC time is associated with the current playback position.

I'd like to adjust this slightly to make better use of markers. What I have in mind is have the user locate the sync frame in the video, then use a "Set Sync" tool similar to "Set Exit" (maybe we can factor out some `SetMarker` code or something like that) to create a "SYNC" marker for a particular session/time. Any time the "Set Sync" tool is used, an offset from video time to UTC time in the video dock is updated. The video cursor could always be drawn (instead of being drawn only when the mouse cursor is not in the plot dock) as a dashed line, which would always coincide with the tip of the "SYNC" marker above the plot. The user could click and drag the sync marker to move the playback position directly to some event.

## Sharing Between Plots

Video sync is one example of something I'd like to use heavily in FlySight Viewer 2: docks should be connected in intuitive ways, so that moving your cursor in one dock also gives you information about the data in other docks. For example, the cursor model at the moment allowes users to move the mouse cursor in the plot dock and see the effect in the legend dock (plot values and measurements based on the cusor) and in the map dock (as positions for one or more sessions at that point in time). This gives a huge amount of intuition for users--they can immediately form connections between different ways of looking at the data.

## Map Dock

The map dock is built on a Qt WebEngine widget which displays a Google Maps satellite image. On top of that, we draw GNSS tracks for all visible sessions. The map dock connects to the cursor model and displays the current cursor position as dots on each track. The user can also move the mouse in the map dock to move the cursor on a particular track. In that case, the plot dock updates to show where in the data that particular point lies. This is a good example of the kind of interaction betweeen plots I described above.

The map dock currently includes a basic Google Maps interface (map type selection and +/- for zooming), but I think in the long run we'll want to remove this and rely on FlySight Viewer native elements for these functions. For example, the map type selection isn't something users change often, and could be relegated to preferences (possibly with a default value as part of "saved layouts" described below).

For panning zooming, we support click and drag and scroll actions right now, but ultimately I want users to be able to use pinch gestures etc. as well. We want navigation in the map to feel completely natural.

The other thing I want to add to the map is the ability to click and drag to measure distances. Currently, we have tool modes for the plot dock, but nothing similar for other docks. This measurement feature may suggest that we can generalize tool modes in some way. I'm not sure we want to have tool modes apply across docks, as they feel specific to individual docks, but, e.g., in the map dock, we might add a small toolbar at the top which allows the user to select between different modes. Would it make sense to add a similar interface in the plot dock, to keep interfaces consistent between docks, or would this just take up too much space in the plot dock?

## Legend Dock

In the previous version of FlySight Viewer, when the user hovered over the map, a tooltip was displayed which could contain plot values at that point or measurements across a span of time, depending on the plot tool mode.

In the new version, this functionality has been moved to the legend dock, which responds to the cursor model in the same way as many other docks. The legend dock shows plot values at the current cursor position or measurements across a span of time, similar to the old version of FlySight Viewer. However:

1. The legend can be poositioned by the user to stay out of the way of the plot.
2. The legend can also be driven by other docks. For example, when the mouse cursor is in the video dock and a synced video is playing, the legend shows plot values at the current playback position.

Again, this dock offers the user a different "view" of the data--as they're moving their cursor around, they can quickly scan the legend dock to see numerical values.

## Layouts

We're currently using KDDockWidgets to manage dock layout. I'd like to make layout (and maybe things like default visible plots and markers) attributes of "saved layouts". FlySight Viewer 2 can ship with a few saved layouts that are useful for certain tasks (like analyzing canopy flights), but I also want to make sure users can create their own layouts (e.g., by setting everything up the way they want and then saving the layout with a name). Users should be able to switch quickly between these layouts (perhaps in a Layout menu) as well as export or import layouts. The current set of layouts could be stored in the same folder as the persistent logbook, so that users can easily back up important application elements.

## Embedded Python Interpreter

Broadly, I want to make sure that advanced features don't clutter the interface, which should feel simple and intuitive, but I want it to be possible for power users to implement advanced analysis. The embedded Python interpreter enables this. The Python interface allows the user to define:

* **Custom calculations**: These allow the user to calculate new values based on existing ones
* **Custom plots**: These are allow the user to define new plots with default colour, units, etc.
* **Custom markers**: These allow the user to define markers based on more complex calculations

Within the interface, custom calculations/plots/markers should have the same representation as their built-in counterparts, just with the implementation in a Python script instead of in C/C++ code.

## Preferences

We've created a hierarchical preference system based on string labels which makes it easy to access preferences within the application, but also to manage these preferences in the preferences dialog.
